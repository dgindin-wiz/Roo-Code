# Code Index Memory Leak Investigation Summary

## Date: 2026-03-31

## Problem
During code indexing of large workspaces (e.g., "wiz" with ~15K files, ~330K code blocks), the VS Code Extension Host's RSS memory grows monotonically from ~500 MB to 2.6+ GB over ~1600 batches (38 minutes), eventually triggering OOM kills. The V8 JavaScript heap stays flat at ~150 MB throughout — the growth is entirely in **V8 "external" memory** (native C++ allocations tracked by V8 but not in the JS heap).

## Environment
- **Platform**: macOS, Apple Silicon (arm64), Node 22.22.1
- **Embedding Provider**: OpenAI-compatible (local `text-embedding-embeddinggemma-300m`)
- **Vector Store**: Qdrant (localhost:6333), `@qdrant/js-client-rest` v1.14.0
- **OpenAI SDK**: `openai` npm package (v4.x)
- **Batch Config**: 200 blocks/batch, up to 10 concurrent batches (`BATCH_PROCESSING_CONCURRENCY = 10`)

## Architecture
The indexing pipeline in `scanner.ts._processBatch()` does three HTTP operations per batch:
1. **deletePointsByMultipleFilePaths** → Qdrant HTTP (delete old points)
2. **embedder.createEmbeddings** → OpenAI-compatible HTTP API (get 200 embedding vectors)
3. **qdrantClient.upsertPoints** → Qdrant HTTP (insert 200 points with vectors)

With `BATCH_PROCESSING_CONCURRENCY = 10`, up to 10 batches run simultaneously, meaning up to 30 concurrent HTTP calls at peak.

## Key Files
- `src/services/code-index/processors/scanner.ts` — batch orchestration (`_processBatch`, `_runEmbedPhase`)
- `src/services/code-index/embedders/openai-compatible.ts` — OpenAI SDK embedding calls
- `src/services/code-index/embedders/openrouter.ts` — OpenRouter embedding calls
- `src/services/code-index/embedders/openai.ts` — OpenAI native embedding calls
- `src/services/code-index/vector-store/qdrant-client.ts` — Qdrant vector DB client
- `src/services/code-index/embedders/ephemeral-fetch.ts` — (NEW) custom fetch with short-lived undici Agent
- `src/services/code-index/debug-logger.ts` — diagnostic logging infrastructure

## What We Know

### Memory breakdown (`process.memoryUsage()`)
| Field | Behavior | Notes |
|-------|----------|-------|
| `heapUsed` | Flat ~150 MB | JS heap is not leaking |
| `heapTotal` | Flat ~200 MB | V8 heap properly bounded |
| `external` | Grows 53 → 2064 MB | **This is the leak** |
| `arrayBuffers` | Always 0 | Not ArrayBuffer-related |
| `rss` | Grows 500 → 2600+ MB | Tracks external growth |

### What "external" means
V8 "external" memory is native C++ memory that has been registered with V8's garbage collector via `Isolate::AdjustAmountOfExternalAllocatedMemory()`. In Node.js, this is primarily:
- **TLS/SSL context buffers** from HTTPS connections (OpenSSL)
- **HTTP response body buffers** held by undici (Node's internal HTTP client)
- **Connection pool state** in undici Agents

### Per-step profiling results
We added memory snapshots before/after each HTTP operation in every batch:

```
Scanner.mem-profile | batchNum=N startExt=X dDel=A dEmb=B dUps=C endExt=Y totalDelta=Z
Embedder.mem-profile | preHttpExt=X postHttpExt=Y postDecodeExt=Z httpDelta=D decodeDelta=0
Qdrant.upsert-mem | preExt=X postExt=Y delta=D pointCount=200
```

**Key findings from per-step profiling:**
1. **Within a single batch**, deltas oscillate near zero (±10-50 MB)
2. The **floor** of `startExt` rises in plateaus over hundreds of batches
3. `dEmb` (embedding HTTP call) typically +10-45 MB per call, but drops back on next batch
4. `dUps` (Qdrant upsert) typically +6-7 MB per call
5. `decodeDelta` is always 0 — base64 decode + buffer release is NOT leaking

### What we tried and results

| Fix Attempted | Effect on externalMB growth |
|---------------|---------------------------|
| Eager null of `response.data` / `item.embedding` in embedder | No measurable effect |
| `resetClient()` — recreate OpenAI SDK client every 25 batches | No effect (old Agent still has live libuv handles, GC can't collect) |
| `resetClient()` on QdrantVectorStore — recreate QdrantClient every 25 batches | No effect (Qdrant's undici Agent is in a closure, inaccessible) |
| `Connection: close` header on OpenAI SDK | No effect (SDK/undici ignores this header) |
| `maxConnections: 2` on QdrantClient constructor | Slight reduction, not conclusive |
| **`ephemeralFetch`** — custom `fetch` using dedicated `undici.Agent` with `keepAliveTimeout: 10ms` | **Cut growth rate ~50%** (1.25 → 0.6 MB/batch) |

### Growth rate comparison
| Configuration | externalMB at batch 400 | Growth rate |
|---------------|------------------------|-------------|
| Original (no fixes) | ~900 MB | ~1.25 MB/batch |
| With ephemeralFetch on OpenAI SDK | ~513 MB | ~0.6 MB/batch |

The ephemeral fetch confirming ~50% of the leak is from the **OpenAI SDK's HTTP client**, and ~50% is from the **Qdrant client's HTTP client**.

## Root Cause Analysis

Both the OpenAI SDK and the Qdrant JS client use `undici` as their HTTP layer:
- **OpenAI SDK**: Uses `globalThis.fetch` which in Node 22 is backed by `undici`'s global Agent
- **Qdrant JS client** (`@qdrant/js-client-rest` v1.14.0): Creates its own `undici.Agent` with 25 connections in `dispatcher.js`, passed as `dispatcher` to the Fetcher

The undici Agent maintains a persistent connection pool with keep-alive. Each HTTP connection holds native TLS buffers (OpenSSL contexts, read/write BIO buffers). Under high concurrency (10 simultaneous batches), many connections are created. The keep-alive timeout prevents connection teardown, so native buffers accumulate.

**Why the Agent can't be freed:**
- The OpenAI SDK's fetch can be overridden (we did this), but the SDK may also hold internal references
- The Qdrant client's Agent is created inside a closure in `api-client.js` → `createClient()` → `createDispatcher()` and is NOT accessible from outside
- `resetClient()` (creating a new client instance) doesn't work because the old Agent has active libuv socket/timer handles that prevent garbage collection

## What Hasn't Been Tried
1. **Serializing batches** (concurrency=1) — would cap connection pool at 1 active connection but 3-4x slower
2. **RSS circuit breaker** — pause indexing at RSS threshold, close/recreate all clients, force GC, resume
3. **Forking embedding work** to a child process that can be killed/restarted periodically
4. **Using a different HTTP client** (e.g., `node:http`) for the OpenAI-compatible API instead of the SDK
5. **Patching undici Agent options** — monkey-patching the Qdrant client's internal dispatcher to use shorter keepAlive

## Diagnostic Logging
The current build includes these diagnostic log entries in `~/roo-index-debug.log`:
- `Scanner.mem-profile` — every batch: `startExt`, `dDel`, `dEmb`, `dUps`, `endExt`, `totalDelta`, `vectorKB`
- `Embedder.mem-profile` — when |delta| > 5MB: `preHttpExt`, `postHttpExt`, `postDecodeExt`, `httpDelta`, `decodeDelta`
- `Qdrant.upsert-mem` — when |delta| > 5MB: `preExt`, `postExt`, `delta`, `pointCount`
- `Qdrant.delete-mem` — when |delta| > 5MB: `preExt`, `postExt`, `delta`, `fileCount`
- `Scanner.memory-breakdown` — every 10 batches: full `process.memoryUsage()` breakdown

## Reproduction
1. Open a large workspace (15K+ files) in VS Code with the extension
2. Configure OpenAI-compatible embedding provider pointing to a local model server
3. Start codebase indexing (clean — purge Qdrant collection first)
4. Monitor `~/roo-index-debug.log` for `memory-breakdown` entries
5. RSS will grow ~1.25 MB/batch (or ~0.6 MB/batch with ephemeralFetch)
